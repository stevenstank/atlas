`fb4bbdb`, measured with benchmark suite version 1
([../BENCHMARKS.md](../BENCHMARKS.md)) under decision D-007
([../DECISIONS.md](../DECISIONS.md)). It records measurements only; the
bottleneck analysis is a separate document.

## 2. Commands

From the repository root:

```
internal/bench/baseline.sh ~/atlas-bench-data/2026-10-06-ryzen7-7435hs-wsl2
cd ~/atlas-bench-data/2026-10-06-ryzen7-7435hs-wsl2
go run golang.org/x/perf/cmd/benchstat@v0.0.0-20260929162123-406019bb8b68 A.txt B.txt
```

`baseline.sh` builds `atlasbench`, then runs set A (10 rounds of every
workload in suite order) and set B (10 rounds in reverse order). Each run is
one `atlasbench -bench NAME -format bench` process for one workload. There was
no warm-up run. Raw results (`A.txt`, `B.txt`), the `benchstat` output, the
profiles, and `summarize.py` (which produced the tables in sections 5, 7, and
8 from `A.txt` and `B.txt`) are kept in that directory, outside the
repository.

## 3. Benchmark matrix and semantic oracles

21 workloads, each run 20 times (10 per set): B1; B2 with D=4 and
K ∈ {10, 20, 40}; B3; B4; B5 with N ∈ {3, 4, 5, 6}; B6 with 3 messages and
capacity ∈ {2, 3, 4}; B7 (8 tasks, 2 workers, 1 crash); B8 with D=4,
K ∈ {10, 20, 40}, and payload ∈ {64, 256} bytes; and V1 (Register, 3 clients,
2 ops, held out). Expected results and their provenance are in
`internal/bench/workloads.go`.

**All 420 runs passed their semantic check** (status, states, transitions,
and for B4 and B7 the invariant, the trace length, and the replay of the
expected trace). `atlasbench` prints nothing on stdout for a wrong result,
and `baseline.sh` stops at the first failed run; neither happened. The states
and transitions in the tables below are those checked values.

**What benchstat says.**
- **Time (`sec/op`).** 18 of 21 workloads show no significant difference
  (`~`). Three differ at p < 0.05: B2/k=20 (+3.68%), B5/n=4 (−2.83%), and
  B8/pad=64/k=40 (−3.32%). With 21 comparisons at α = 0.05, about one false
  positive is expected by chance; three is more than that, so for these
  workloads differences of about 4% are not resolved on this machine.
- **Allocations (`B/op`, `allocs/op`).** Identical medians in both sets for
  every workload. B5/n=6 `allocs/op` is flagged at p = 0.020 with a median
  change of −0.00%.
- **Peak RSS.** No significant difference for any workload.
- **GC cycles.** No significant difference. **GC CPU fraction** differs for
  B5/n=6 (−13.45%, p = 0.027) and has wide spreads (up to ±101%) elsewhere;
  it is a runtime/metrics estimate, and it is only produced for runs in which
  at least one GC cycle ran (the runtime updates its CPU-class counters at
  GC), so the small workloads have no value.
- **Noisy workloads.** The microsecond-scale workloads (B1, B4, B5/n=3,
  B6/cap=2..4) have wide spreads: ±16% to ±81% in `sec/op`, single outliers up
  to 3.5× the median (B1, set B; see the min–max columns above). Their times are not
  precise; process start-up and scheduling dominate at that scale.

## 6. Peak RSS

`peak-rss-bytes` is the kernel's peak resident set size of the `atlasbench`
process (`getrusage` `ru_maxrss`), read right after `check.Run` returns. It is
resident memory, not Go heap, and includes the runtime's baseline: about
4 MiB, which is all the small workloads show. Medians are in section 4 and the
benchstat table.

**Cross-check.** One extra run of each large workload under `/usr/bin/time
-v` (not part of the sets) gave a maximum resident set size equal to the
driver's `peak-rss-bytes` within 0.03%: B2/k=40, B3, B7, and
B8/pad=256/k=40.

## 10. Run hygiene

- Observable: 1/5/15-minute load average before the sets `0.28 0.35 0.26`,
  after `1.11 1.00 0.59` (consistent with the benchmark runs themselves). Free memory before: `8489` MiB of
  `11804` MiB visible to WSL; the largest workload peaked near
  1.4 GiB RSS, so there was no memory pressure.
- No other work was started from this session during the sets; the two sets
  ran back to back in one command (4 min 41 s).
- **Not observable or not controlled:** what else ran on the Windows host,
  the Windows power plan and whether the laptop was on mains power, CPU
  frequency scaling and thermal state, and WSL's own background activity.
  None of these were controlled. Treat the results as specific to this
  machine in this state, and compare only with result sets from it.

## 11. Anomalies and failures

- No semantic failures; no failed or discarded runs.
- Three time comparisons differ significantly between the sets (section 5).
- Microsecond-scale workloads are noisy (section 5).
- GC CPU fraction is unavailable for workloads with no GC cycle, and noisy
  where it exists.
- The tree was dirty (section 1), although the engine code was unchanged.
